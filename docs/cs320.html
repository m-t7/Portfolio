Why I Selected This Artifact

ContactService is a Java application created in CS 320, Software Test, Automation, and Quality Assurance. It was originally designed as an in-memory contact management service that provides CRUD operations for contact records containing a unique ID, first name, last name, phone number, and address. I selected this artifact because it demonstrates my ability to design maintainable software while applying object-oriented principles, input validation, and software testing to build a reliable application.

This artifact demonstrates my ability to improve software design by extending a console-based service into a complete desktop application. The enhancement replaced the in-memory HashMap with a relational SQLite database using parameterized SQL queries, preserving the existing CRUD interface while adding persistent data storage. These enhancements strengthened the application's usability and scalability, aligning with Course Outcomes 3, 4, and 5 by applying sound software design principles, integrating database technologies, and implementing secure programming practices.

What It Is

A Java contact management service: a Swing form lets a user add, look up, update, and delete contacts, while a ContactService layer validates input and persists records to a SQLite database. A JUnit test suite exercises every CRUD path independently of the UI.

Original Artifact

The original version had no user interface at all: ContactService stored contacts in an in-memory HashMap<String, Contact> and was exercised entirely through ContactServiceTest and ContactTest. There was no persistence layer, so every contact disappeared as soon as the program stopped running.

LayerOriginal
StorageIn-memory HashMap<String, Contact>

Enhancement

  • Persistent storage: replaced the in-memory HashMap with a SQLite database, so contacts survive after the program stops.
  • Parameterized queries: every insert, update, and delete goes through a PreparedStatement instead of string concatenation, keeping the data layer safe from SQL injection.
  • Validation at the domain object: Contact enforces its own length limits and null checks, so invalid data can't reach the database regardless of which caller constructs it.
  • Preserved interface: the CRUD method signatures on ContactService stayed the same, so this was a swap of the storage layer, not a rewrite of the service's contract.

Testing

ContactTest and ContactServiceTest cover the validation rules on the domain object and the full CRUD lifecycle on the service, including expected failures such as an over-length field or a duplicate ID, not just the success paths.

Reflection

During the enhancement process, I gained a better understanding of integrating a relational SQLite database into an existing application while preserving its original functionality. One of the biggest challenges was refactoring the service layer to replace the in-memory data store with a persistent database without changing the existing CRUD behavior. I also learned how to write unit tests that exercise the ContactService and its validation rules directly against the SQLite layer, verifying behavior end to end rather than mocking it out. Building a Swing user interface on top of that layer made the application interactive and its functionality more tangible. The plan from my code review held up well, and the feedback on that plan confirmed the SQLite migration was the right scope for this enhancement rather than something to expand further, so I met the planned course outcomes without significant changes to my original approach. The one thing I'd call partially rather than fully met is test coverage: ContactServiceTest and ContactTest cover the domain and service layer thoroughly, but the Swing UI itself has no automated tests, so that part of the application is still only verified by hand.
