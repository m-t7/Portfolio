Why I Selected This Artifact

Course Planner is a C++ program built for CS 300, Data Structures and Algorithms. It was designed for ABCU University to load course information from a file, store course records, search for courses, display course information, and manage prerequisites. I selected this artifact because it demonstrates my ability to apply algorithms and data structures to solve a practical problem.

This artifact demonstrates my ability to choose appropriate data structures and algorithms to improve the performance of a software solution. The original Course Planner used a binary search tree to store course information. I replaced the tree with an unordered_map for faster course lookups, added a new discipline index to make searching more efficient, and implemented a breadth-first search algorithm to traverse course prerequisites efficiently. This approach created a better software solution while aligning with Course Outcomes 2, 3, and 4 by strengthening my technical communication, algorithmic thinking, and ability to use computing tools effectively.

What It Is

A C++ command-line program that reads a CSV file of course data (number, title, discipline, prerequisites), loads it into a course catalog, and lets a user search for a course, list every course in a discipline, and look up the full prerequisite chain for a course through a simple menu.

Original Artifact

The original version stored every course in a binary search tree keyed on course number, using recursive insert and in-order traversal to print courses in sorted order. Looking up a course or walking its prerequisite chain meant traversing the tree node by node.

OperationOriginal
StorageBinary search tree (Course* nodes with left/right pointers)
Course lookupTree traversal, O(log n) average
Prerequisite lookupNo dedicated traversal; handled ad hoc through the tree

Enhancement

  • Course lookup: replaced the binary search tree with unordered_map<string, Course> keyed on course ID, so a single lookup is O(1) average instead of a tree walk.
  • Discipline index: added a second unordered_map<string, vector<string>>, so listing every course in a discipline no longer means scanning the whole catalog.
  • Prerequisite traversal: implemented a breadth-first search that starts from a course, walks its prerequisite edges level by level with a queue, and tracks visited courses so it terminates cleanly even if prerequisite chains overlap.
Course lookup:        unordered_map<courseId, Course>        O(1) average
Discipline lookup:    unordered_map<discipline, courseId[]>  O(1) average
Prerequisite lookup:  BFS over the prerequisite graph          O(V + E)

Reflection

During the enhancement process, I gained a better understanding of how data structure choices affect the scalability and maintainability of an application. One of the biggest challenges was refactoring the original code while making sure the program continued to work correctly after replacing the binary search tree. I also learned that every design decision involves trade-offs, such as improving lookup speed with a hash table while giving up the automatic sorting a binary search tree provides for free. The plan I presented in my code review held up well against feedback on it, so I was able to achieve my desired outcomes without any major changes to my implementation plan. The one outcome I'd call partially met rather than fully met is testing: unlike the CS 320 contact service, this artifact has no automated test suite, so the lookup, discipline-search, and BFS prerequisite logic are verified by manual runs against the sample data rather than by repeatable unit tests.
