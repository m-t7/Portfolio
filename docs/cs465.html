Why I Selected This Artifact

Travlr Getaways is a full-stack travel booking web application originally built in CS 465, Full Stack Application Development, using the MEAN stack to manage and display vacation packages through a public website and an administrative dashboard. I selected it for my ePortfolio because it demonstrates full-stack software engineering skills, and the enhancement shows my ability to modernize an application by migrating the public-facing Handlebars.js frontend and the internal admin Angular frontend into a unified React micro-frontend architecture that improves maintainability and reusability. I chose Vite over a heavier framework like Next.js since this application isn't being deployed to a production environment or built to scale massively, so a lighter build tool gave me the same standardized React tooling without unnecessary overhead.

This work met the course outcomes I identified in Module One by applying collaborative software design principles, evaluating architectural trade-offs, implementing modern development practices, and improving the application's maintainability and security, all without changing my original outcome plan.

What It Is

Travlr Getaways is a full-stack trip-booking application: a public site where visitors browse trips, and an admin dashboard where staff manage listings. The backend is a Node and Express REST API backed by MongoDB, exposing endpoints such as /api/trips, /api/login, and /api/register.

Original Artifact

The original version served the customer-facing site with Express and Handlebars templates (full server-side rendering) and the admin dashboard as a separate Angular single-page application. Both front ends talked to the same Express/MongoDB API.

Enhancement

  • Frontend rewrite: replaced Handlebars (public site) and Angular (admin dashboard) with React microfrontends (Vite + Tailwind CSS); the legacy app_server and app_admin folders were removed once their replacements were feature-complete.
  • Standard tooling: Vite, Biome, and Tailwind CSS replace three separate toolchains with one.
  • Reusable UI components: TripCard, a trip listing view, and a shared Navbar replace duplicated markup across pages.
  • Security: the original Handlebars template rendered trip descriptions with an unescaped triple-stash ({{{this.description}}}), and the original Angular admin bound them with [innerHTML]. Both render raw HTML from the API. The React rewrite renders descriptions as plain text everywhere, closing that stored-XSS surface.
  • Authentication: the original app already enforced JWT auth on protected trip routes (a backend authenticateJWT middleware returning 401, paired with an Angular HttpInterceptor that attached the token). I carried that same behavior into the React admin app as a shared fetch wrapper that attaches the Authorization header, so the access control isn't new, but the implementation is.

Reflection

Working on this enhancement taught me a lot about building applications with React and Vite. Getting the project set up was one of the hardest parts, but breaking it into smaller pieces and following the documentation made it much easier. I also learned how to plan before making big changes to an application, especially when moving to a new framework. The biggest challenge was rebuilding the frontend, but seeing everything come together made the effort worthwhile.

The plan I walked through in my code review held up well: I didn't need to change my overall approach once I started implementing it, though I made a few smaller structural adjustments as I got deeper into the code than the review alone surfaced, for example, moving the admin app's selected trip code from localStorage to a /edit-trip/:code route param once I saw how fragile that coupling actually was.

There are still a few enhancements I'd like to make, such as improving the site's responsiveness and replacing some of the outdated images with SVGs or simple CSS styling for a more modern look and feel. I intentionally kept the scope of this enhancement manageable given time constraints, so I'd call the production-polish part of my plan partially rather than fully met: the architecture and security work are done, but the visual and responsive polish is real, remaining work rather than a finished stretch goal.
